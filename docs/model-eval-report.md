# M2 双模型调查评测

## 复现与判分

在 v2 根目录按 README 配置两组凭据，执行 `bun install --frozen-lockfile`、`bun run eval:privacy`、`LIVE_MODEL=0 bun run eval:paired`、`LIVE_MODEL=1 bun run eval:compare`。下表使用 2026-11-24 的单次全量结果。两个模型并行启动，每个模型依次处理同样的 8 对夹具，每例使用独立内存库、工单和脱敏绑定。DeepSeek 使用 Pi Chat Completions，OpenAI 使用 Pi Responses、最低可用推理档位 low。模型服务的采样与延迟可能随运行波动。

单例通过须正常结束、未触发出站探针、引用该例每个指定来源的真实 evidenceId，并输出唯一正确代码。线上与离线调用同一判定函数。仅放宽大小写、分隔符和 Markdown 标记，不用预期答案反推自然语言结论。成对全对要求两个分支均通过。引用检查能确认来源，无法验证每句解释。Mock 根据夹具规则作答，其 16/16 是回归结果。

## 错例复核与选型

- 新协议下，DeepSeek 的 1B 已识别同主体，但将后续申请 viewer 当成当前结论。2A 的正文明确无需续期却给出 CHECK_ACCESS。8B 的正文明确拒绝 admin，同时选了 REQUEST_VIEWER。三例都保留原判分；单代码指标混合了事实理解、行动选择和输出格式。
- DeepSeek 的 5B 在目录组为空时优先采信两个分支共有的同步待处理标记，未抓住上游组成员缺失。4A 对已记录的刷新继续要求核实，7B 则已正确指出角色清单不可用。DeepSeek 总分比基线少 1 例，成对得分持平，不能据此声称协议带来总体收益。
- 两模型均错在 3A。GPT 正确读出日志晚一天，也区分了采集时间，但认为缺少追踪 ID、无法关联。夹具把故障日及以后的日志一律标作 USE_LOG。模型的时序解释合理，STALE_LOG 也不能准确表达“相关性待核实”。应在后续独立评测中提供关联证据或设立待核验类别。
- 在这组只读调查上优先选 GPT，正确案例更多且工具与 Token 更少，累计耗时多约 19 秒。DeepSeek 适合对延迟敏感且有人复核的路径。未测单价、生产故障分布或多轮置信区间。协议与解析器同时变更，旧版无摘要，无法独立估算两项改动的贡献。
- 初次联调时 Pi 默认发送的推理档位 none 被 GPT 接口拒绝，同轮 DeepSeek 为 7/16、0/8 对。表中采用修复到 low 后两模型均完成的整轮结果。原始基线和本轮逐例记录分别位于 `eval-output/paired-live.json` 和 `eval-output/compare-live.json`。

## DeepSeek high 复测（2026-11-24）

真实探测使用 Pi 的 `completeSimple` 发送一条无业务数据的算术题。出站请求包含 `thinking: {"type":"enabled"}` 和 `reasoning_effort: "high"`。响应正常结束，Pi 解析到 68 个字符的非空 thinking 块，输出计量为 29 Token。探测证实开启了思考；单凭这一请求无法验证服务端对 high 与其他已开启档位分配的计算量。

确认探测后运行 `LIVE_MODEL=1 MODEL_REASONING=high bun src/eval/paired.ts > eval-output/deepseek-high.json`。16 例沿用原调查协议、四个只读工具、脱敏网关和判分器。历史两列来自同日此前的 compare-live.json，新列为独立单轮测量。
